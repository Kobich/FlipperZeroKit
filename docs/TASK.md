# Основная задача: Android-приложение для обмена с Flipper Zero

Зафиксировано: 24 ноября 2026. Источник — задание на присланном пользователем снимке.
Этот документ определяет функциональную цель проекта. Очередность и статус работ ведём в [ROADMAP.md](ROADMAP.md), фактические проверки — в [VALIDATION.md](VALIDATION.md).
Новые указания пользователя имеют приоритет; принятые изменения затем отражаем здесь и в плане.

## 1. Цель

Разработать Android-приложение-передатчик, которое подключается к Flipper Zero, показывает его состояние и сведения, получает файлы с устройства и отправляет выбранные на телефоне файлы обратно.
Пользователь видит состояние соединения, актуальные данные, ход передачи и её конечный результат.
Повторный вход должен сопровождаться автоматической попыткой восстановить ранее использовавшееся соединение.
Отправка на Flipper — обязательная часть задания с отдельным этапом проверки экспериментального сценария.

## 2. Исходное задание

Ниже — расшифровка снимка. Пунктуация и опечатки приведены к читаемому виду, смысл требований сохранён.
[Оригинал снимка](requirements/original-task.png) сохранён в репозитории.

### Необходимый функционал

- Подключение к Flipper Zero и установка канала общения.
- Получение информации о Flipper Zero: заряд батареи и системные характеристики; для этого у Flipper есть специальные proto-структуры.
- Получение файлов, которые есть в файловой системе Flipper Zero.
- Выбор файлов во внутреннем хранилище и их отправка на Flipper Zero. В исходном тексте отмечено, что эта опция экспериментальная даже в базовом Flipper App, поэтому возможным проблемам нужно уделить внимание.

### Требования к интерфейсу

- UI для подключения и установки общения с Flipper Zero.
- Отображение статуса подключения к Flipper Zero.
- Визуализация файлов, находящихся на Flipper, с кнопкой обновления данных.
- UI выбора файлов для передачи на Flipper.
- Визуализация прогресса передачи данных с индикацией завершённости операции.
- Отображение заряда батареи и системных характеристик, полученных с помощью специальных proto-структур.

### Постановка задачи

1. Реализовать установку соединения между смартфоном и Flipper с автоматической попыткой переустановки соединения при повторном входе.
2. Реализовать подготовку данных для отправки на Flipper с учётом особенностей протокола обмена.
3. Реализовать обработку данных после получения пакетов от Flipper с учётом особенностей протокола обмена.
4. Реализовать proto-модели, необходимые для функций приёма и передачи данных.
5. Реализовать получение информации о подключённом Flipper.
6. Реализовать получение файлов от Flipper.
7. Реализовать отправку файлов на Flipper.

## 3. Рабочая трактовка

Эти решения нужны для конкретного плана; они отделены от исходного текста и могут уточняться пользователем.

- «Получение файлов» включает список/навигацию и скачивание выбранного файла на телефон. В исходнике скачивание отдельно не детализировано; эта трактовка реализована, скачивание подтверждено пользователем.
- Под «внутренним хранилищем» для выбора отправляемого файла понимаем доступные пользователю локальные файлы телефона, а не только приватный каталог приложения.
- Повторный вход рассматриваем как возврат в приложение/сценарий подключения и новый запуск после закрытия. Восстанавливается последнее выбранное устройство; конкретное событие lifecycle уточняем при реализации.
- Базовый сценарий — один выбранный файл и одна активная файловая операция. Пакетную очередь и возобновление передачи с места обрыва исходное задание не описывает.
- По уточнению пользователя 24.11.2026 Flipper — одна фича нижней навигации большого приложения. Вся фича остаётся одним модулем :flipper, готовый UI — блок ui внутри него; :sample — демонстрационный хост. Внутри фичи общий экран с блоками устройства/передачи/файлов, а не отдельные глобальные пункты.
- Основное устройство для первой физической проверки — телефон пользователя с Android 16. Версия firmware Flipper пока неизвестна; её нужно записать при проверке DeviceInfo.

Обязательные пользовательские сценарии:

1. Подключиться к Flipper и увидеть готовность общения.
2. Повторно войти и увидеть автоматическую попытку восстановления связи.
3. Получить сведения и заряд с настоящего устройства.
4. Открыть каталог Flipper и обновить список файлов.
5. Выбрать файл Flipper и получить его на телефон с прогрессом и конечным результатом.
6. Выбрать локальный файл, отправить на Flipper, увидеть завершение и полученный файл.
7. При отказе в разрешениях, выключенном Bluetooth, timeout и разрыве соединения увидеть понятное состояние и возможность повторить действие.

## 5. Архитектурные границы

- :flipper — единая Android Library: api/model, internal BLE/RPC/proto/файловые операции и UI-блок dev.flipper.ui с FlipperScreen, общими UI-блоками/SAF/состояниями. Hilt и Activity модулю не нужны.
- :sample — пример хоста: внешний NavHost/нижний бар, Hilt, тема и владелец клиента. Сохранение устройства/reconnect встроены в UI по умолчанию и могут быть заменены контроллером хоста.
- URI/потоки телефона открывает UI-слой через application ContentResolver. BLE/RPC API принимает потоки, не Activity/URI/пикеры. UI ViewModel не удерживает Context/Activity.
- Размер блока Storage и размер BLE-фрагмента — разные уровни. Крупный файл передаётся потоком, а не собирается целиком в ByteArray.
- Завершение передачи определяется протоколом файловой операции; успешный GATT write сам по себе не подтверждает сохранение файла.
- Репозиторий коллеги остаётся источником для чтения. Разработка ведётся только в FlipperZeroKit.

Для выбора источника/назначения на Android используем системный Storage Access Framework: выбор возвращает URI, с которым работает хост через поток. Основание — [документация Android](https://developer.android.com/training/data-storage/shared/documents-files?hl=en).

## 7. Решения пользователя и выбранная реализация — 24.11.2026

Эта таблица заменяет прежние рабочие допущения об отказе существующему имени, оставлении частичного файла, ручном восстановлении, вкладках и лимите 10 минут. «Реализовано» означает наличие кода; физическая проверка нового поведения ещё нужна. Паузы reconnect и технические таймауты выбраны агентом как пробная политика по просьбе пользователя предложить решения.

| № | Решение / вопрос | Что сделано и как | Что не сделано / осталось |
| --- | --- | --- | --- |
| 1 | При конфликте подбирать (2), (3)… | Upload выбирает свободное имя с сохранением расширения, возвращает фактический путь; передача через UUID-временный файл, затем MD5, публикация и повторный MD5. При скачивании имя обрабатывает SAF-провайдер | Нет UI произвольной перезаписи. Одновременная запись теми же путями другим клиентом не защищена атомарным create/rename в RPC; конкретная firmware требует проверки |
| 2 | Частичный файл удалять | Delete без recursive очищает записанные нами пути. Задачи очистки Flipper сохраняются до первого байта и повторяются при подключении к тому же адресу. Созданные SAF-документы также журналируются, удаляются после сбоя и при следующем запуске с сохранёнными URI-grants | Физически недоступное устройство/провайдер не очищается мгновенно: задача остаётся ожидающей. Проверить offline → reconnect и kill процесса |
| 3 | По возможности отмена без разрыва, иначе восстановить | Upload отменяется на границе целого RPC-кадра; Delete сбрасывает непрерывную запись и удаляет её. При проблеме транспорта/очистки — сброс и ограниченное восстановление. Read не имеет отдельной cancel-команды: сброс и восстановление. Выбор другого устройства/ручной disconnect имеют приоритет | Проверить на firmware пользователя мягкую отмену и fallback; повтор самой передачи не запускается автоматически |
| 4 | Продолжать при уходе в фон | Задача принадлежит foreground service connectedDevice, а не ViewModel. Есть уведомление прогресса/отмены, временное удержание CPU только на время операции и URI-grants. Общий экран можно закрыть, операция остаётся в живом процессе | Android/пользователь может остановить процесс/приложение; автоматического восстановления передачи после этого нет. Проверить Android 16, блокировку и выход с destination |
| 5 | Передавать целиком, без resume | После отмены/ошибки нужна новая целая передача. Восстанавливаются соединение и очистка, а не позиция файла | Resume не реализуем на этом этапе |
| 6 | Пока один файл | Одна активная операция, общий Storage mutex и запрет второго foreground upload/download | Очереди, множественного выбора и папок нет |
| 7 | Имена пока оставить | ASCII-ограничение пути/имени сохранено; Unicode внутри содержимого передаётся как байты | Кириллические имена не поддержаны |
| 8 | Каталоги не ограничивать | Доступны все доступные через RPC каталоги /, /ext, /int и вложенные, ограничения записи задаёт firmware | Дополнительной прикладной песочницы нет |
| 9 | Комфорт без постоянного расхода батареи | В видимой фиче до 3 попыток, паузы 0/2/6 с; после провала cooldown 60 с до нового входа или явный ручной выбор. В фоне без передачи нет цикла переподключения. Явный disconnect/новый поиск выключает автоматический reconnect до ручного выбора устройства. Файловая операция имеет собственную ограниченную попытку восстановления/очистки | Проверить UX и реальные интервалы на Android 16; не делать бесконечное reconnect/сканирование |
| 10 | Сведения оставить как есть | DeviceInfo/PowerInfo при готовности сессии и по кнопке, без периодического polling | Фонового обновления заряда нет |
| 11 | Общий экран с блоками, текущие компоненты | Один LazyColumn: состояние подключения/очистки, устройство/сведения, передача/выбор файла, каталог и строки файлов. Внутренние вкладки удалены. В нижнем баре хоста один Flipper | Финальная визуальная полировка и прогон в целевом хосте |
| 12 | Не ограничивать общую длительность/размер штатным сценарием | Read/Write по умолчанию timeoutMillis=0, без общего лимита; финальный MD5/публикация также ждут пока жива сессия. Сохраняются технические ограничения: таймаут GATT, 60 с без активности потока, 15 с готовности RPC, конечные metadata/cleanup-запросы | Физические ограничения FS/proto, свободного места и Android не исчезают. Скорость/MTU ещё не оптимизировались, больших файлов штатного размера не задаём |

Требования фона/очистки входят в уточнённый объём, а не в дословный текст исходного снимка. Нужна отдельная приёмка новых политик: прежний положительный прогон подтверждал скачивание в старой версии.

## 8. Когда вся задача завершена

R01–R09 закрыты соответствующими пользовательскими сценариями на устройстве, включая экспериментальную отправку и проверку конечных файлов. В VALIDATION.md записаны телефон/Android, firmware Flipper, шаги и результаты; ошибки и отмена не маскируются успешным завершением. Приложение использует реальные данные в готовых сценариях, а модуль :flipper сохраняет библиотечные границы.


26.11.2026: по указанию пользователя файловый браузер вынесен на внутренний экран Files внутри единой фичи; главный содержит компактную кнопку Open files и статус передачи, память SD остаётся в сводке устройства.
